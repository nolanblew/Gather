# Search decision and evidence

Research date: 2026-09-29. This records the implementation recommendation and measured model experiment; the production hybrid ranker needs its own integration checks.

## Decision

Use server-side hybrid lexical/fuzzy search plus local quantized `Xenova/all-MiniLM-L6-v2` embeddings by default. Keep lexical search available immediately during model warm-up and on model failures. The small fixture supports this choice, but does not establish broad retrieval quality. Provide an explicit `SEARCH_PROVIDER=openai` option for GPT-6 Luna reranking; never send queries or notes externally because local search fails. `SEARCH_PROVIDER=fuzzy` disables AI entirely.

MiniLM suits short English notes, and is the smallest evaluated option. Its original model maps short sentences/paragraphs to 384 dimensions and truncates beyond 256 word pieces. Use the ONNX conversion repository with Transformers.js, mean pooling, normalized output, CPU and `dtype: 'q8'`. [Original model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2), [ONNX usage](https://huggingface.co/Xenova/all-MiniLM-L6-v2), [ONNX artifacts](https://huggingface.co/Xenova/all-MiniLM-L6-v2/tree/main/onnx).

## Alternatives

| Model | License | Quantized ONNX bytes measured | Encoding | Tradeoff |
| --- | --- | ---: | --- | --- |
| all-MiniLM-L6-v2 | Apache-2.0 | 22,972,370 | Mean, normalized, 384 dimensions | Smallest; good short paraphrases in this fixture |
| bge-small-en-v1.5 | MIT | 34,014,426 | CLS, normalized, 384 dimensions | Retrieval-oriented; 512 token context; no fixture gain over MiniLM |
| e5-small-v2 | MIT | 34,014,367 | Mean, normalized, 384 dimensions | Strong fixture result, but ~48% larger model and required prefixes |

BGE's card reports stronger general retrieval benchmark performance and advises a query instruction for short-to-long retrieval. Those general benchmarks do not demonstrate better personal-note retrieval. Its cosine distribution requires dataset-specific cutoffs. [BGE model card](https://huggingface.co/BAAI/bge-small-en-v1.5), [BGE ONNX files](https://huggingface.co/Xenova/bge-small-en-v1.5/tree/main/onnx).

E5 requires `query: ` and `passage: ` prefixes for asymmetric retrieval; omitting them degrades performance. Its raw cosine distribution also makes a universal fixed confidence cutoff inappropriate. [E5 model card](https://huggingface.co/intfloat/e5-small-v2), [E5 ONNX files](https://huggingface.co/Xenova/e5-small-v2/tree/main/onnx).

## Actual model evaluation

Ran real CPU inference on Windows with Node **v24.19.0** and **@huggingface/transformers 3.8.1**. Fixture contains 10 distinct personal-list documents and 20 labeled queries: five exact, five misspelled, ten paraphrases. Example paraphrases include `things for sleeping outdoors`, `reimburse business costs`, `food without meat for tonight`, and `something to block sound for father`. Every model used q8. Scripts and raw rankings are available locally in ignored `output/search-eval/eval.mjs` and `output/search-eval/results.json`.

| Model | Top 1 / 20 | Top 3 / 20 | Paraphrase top 1 / 10 | Warm 20-query batch | Process RSS after inference |
| --- | ---: | ---: | ---: | ---: | ---: |
| MiniLM | 19 | 19 | 10 | 19 ms | 143 MiB |
| BGE | 19 | 19 | 10 | 40 ms | 182 MiB |
| E5 | 20 | 20 | 10 | 32 ms | 192 MiB |

MiniLM ranked the target for `gardning present` fourth; BGE ranked it sixth. This is a concrete reason to retain lexical typo matching. The timings are one-machine batch observations, not a per-request latency promise. RSS includes Node/native libraries and later rows follow earlier models in the same process, so they are indicative rather than isolated model memory costs. First-run load plus document encoding was ~1.27 s MiniLM, ~0.90 s BGE, ~1.03 s E5; cached repeat was 217/262/236 ms. These are not measured cold-network download durations.

Model cache for the experiment: `output/search-eval/model-cache/Xenova/<model>/`, containing tokenizer/config files and `onnx/model_quantized.onnx`. MiniLM's model+tokenizer/config total is ~23.7 MB. Persist the production model cache under the mounted data volume, separate from the workspace JSON. Embedding cache is disposable/rebuildable and must not count toward the 5 MiB workspace export limit.

Acceptance gates for the integrated hybrid ranker: exact 5/5 top 1; fuzzy 5/5 top 3; paraphrase at least 9/10 top 3 and 8/10 top 1; zero scope/category leaks; edited/deleted/imported content never returned stale; lexical response within 250 ms on the fixture while the model warms. Add confusing near-neighbor lists and unseen paraphrases before describing quality as generally strong. Include blank/nonsense queries and bound unrelated semantic results using a threshold calibrated on the actual chunk fixture, not a universal cosine value.

The permanent real-model integration experiment is `tests/search-eval.mjs` (run separately from offline unit tests). It measured exact **5/5 top 1**, fuzzy **5/5 top 3**, paraphrase **9/10 top 1 and 10/10 top 3**, and **5/5 unrelated queries with no matches**. A 2,700-character note tail was found by the paraphrase `ice climbing boots`, with item/section IDs and the tail text in its evidence snippet. Section and category field checks also passed. Cached Windows execution took 418 ms including the fixture's warm-up and all queries, with whole-process RSS 151 MiB; this is not a Docker or cold-download measurement. The fixture motivated cosine floors of 0.35 for title-only semantic matches and 0.28 for other chunks: a query about submarine torpedoes incorrectly matched the bare title `House repairs` at ~0.314, while the relevant expense-reimbursement paragraph scored ~0.294. These thresholds are empirical fixture settings, not universal confidence guarantees.

## Data and ranking architecture

The existing store persists one validated JSON workspace in SQLite, bounded to 5 MiB, 1,000 lists and 20,000 items. Search can scan all scoped lexical documents and normalized cached vectors without adding a vector database.

1. Apply `scope` (`library`, `favorites`, `templates`, `archive`, `all`) and `categoryId` filters before ranking, candidate selection or hosted requests.
2. Build metadata chunks from list title/category/description and section title. Build separate item chunks from title/category/section plus item text/quantity/note. Split long descriptions and notes into short overlapping segments, so relevant text near the end is not silently lost to MiniLM's context limit. Preserve `listId`, optional `itemId`/`sectionId`, field and source text for matching snippets.
3. Cache vectors separately in SQLite keyed by stable chunk ID, content hash, model ID/revision, dtype, pooling and chunk-format version. A list/category/section rename changes dependent item chunk hashes. Deleted/replaced IDs are pruned. Never include a cached vector whose current content hash differs.
4. Normalize embeddings and compare cosine via dot product. Score every scoped list using its strongest relevant chunk, then combine semantic rank with fuzzy token/edit-distance rank and strong exact phrase/title/substring boosts. Keep exact titles above loose semantic results. Avoid raw arbitrary weights dominating exact matches; reciprocal-rank fusion is a reasonable starting point. Deterministically tie-break by stable position/ID.
5. Build missing vectors in bounded batches using one shared pipeline and a concurrency limit. Do not make a search request wait for the complete 20,000-item index. Return lexical results with `warming`/`degraded` status when the bounded semantic deadline expires, and retry local indexing separately with backoff. Re-read/filter current source before returning IDs so a concurrent mutation cannot surface deleted content. Production indexing encodes at most 64 chunks per search by default, eight per batch, yielding between batches. It prioritizes current scope and lexical hits. It caps the disposable cache at 4,096 embeddings (about 6 MiB raw vectors), with configurable hard maximum 8,192. An active search keeps requesting bounded indexing work until its scoped target is covered. If the scope exceeds the vector cap, the deterministic target favors lexical hits and then workspace order; the response remains `partial:true` but stops warming after the target is covered, preventing repeated eviction and re-encoding. Text search continues to cover all scoped fields. Changing scope or editing content selects a new target and evicts vectors outside it when needed.

API contract: `POST /api/search` with `{query, scope, categoryId}`; a small JSON body limit, e.g. 8 KiB, plus query length <=500 characters. Reuse same-origin checking even though search is read-only, since hosted mode can consume API budget. Return `{results:[{listId,score,match:{itemId?,sectionId?,text,field},matchType:'exact'|'fuzzy'|'semantic'}],provider,status,reason?}`. Reasons must be safe status codes/messages, never raw upstream errors or secrets. `GET /api/search/status` reports provider/model/state without key/config secrets. Health remains healthy if optional semantic search is unavailable.

React should debounce ~200 ms, abort the previous request and guard responses with a request sequence. Query, scope, category and workspace revision must all be dependencies. A successful action/import triggers a fresh search and invalidates results before stale promises settle. Current-collection versus entire-workspace search maps onto the same scoped endpoint. Immediate local lexical display while waiting prevents an empty/loading flash.

## Docker/runtime compatibility

Transformers.js officially supports server-side Node ESM inference. ONNX Runtime supplies native CPU binaries for Windows x64/arm64 and Linux x64/arm64. Windows and the actual Debian Node 24 Docker runtime were both verified. [Node inference guide](https://huggingface.co/docs/transformers.js/v3.8.1/en/tutorials/node), [ONNX Node platform support](https://onnxruntime.ai/docs/get-started/with-javascript/node.html).

The runtime Docker stage copies production Linux dependencies after pruning development tools. Native dependency build scripts are explicitly enabled, CUDA installation is skipped, and inference uses CPU. The non-root `node` user writes the model and vector caches in the mounted data volume. Model warm-up does not block server startup/health. A persisted cache allows subsequent operation without downloads; an explicitly offline installation needs prefetched model artifacts.

To share a miniature PC with media services, production inference is lazy (first nonblank local search), uses one intra-op and one inter-op ONNX thread, serializes native inference, and disposes the model after five idle minutes while retaining cached vectors. `SEARCH_IDLE_MS` defaults to 300000 (bounded 1000–3600000); `SEARCH_MAX_EMBEDDINGS` defaults to 4096 (bounded 128–8192); `SEARCH_INDEX_BATCH_LIMIT` defaults to 64 (bounded 8–128). The 512 MiB/0.5 CPU container limit is an operator resource budget to verify against the final image, rather than a measured capacity promise for all workspaces.

Root integration verification on Linux Node 24.21.0, in a Docker container limited to 0.5 CPU/512 MiB, reproduced all real-model gates: exact 5/5 top one, fuzzy 5/5 top three, paraphrase 9/10 top one and 10/10 top three, all five negatives empty, long-note tail and section/category matches. The cached-model fixture took 1,768 ms including initialization and reported 179 MiB process RSS. These are small-fixture observations, not hardware-wide guarantees. Service observations: about 19 MiB before model use, 104 MiB after a query, and 89 MiB after a shortened five-second idle-disposal test. Native libraries/allocators retain memory after model disposal. A cold first query returned a warming response in 1,072 ms; a later cached query returned ready in 202 ms. Health remained available during loading. Docker inspection confirmed the CPU, memory and PID limits.

## Hosted option and controls

Official OpenAI documentation currently lists **`gpt-6-luna`**, supports low and medium reasoning effort, Responses API, and Structured Outputs. Keep the model literal overrideable through `SEARCH_OPENAI_MODEL`, with `SEARCH_REASONING_EFFORT=low|medium` (default low). The API page confirms availability in the catalog; the deployment's actual key/account entitlement still requires its first configured request. [GPT-6 Luna model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna), [Models catalog](https://developers.openai.com/api/docs/models), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Use `SEARCH_PROVIDER=local|fuzzy|openai` (default local), `OPENAI_API_KEY`, `SEARCH_OPENAI_MODEL=gpt-6-luna`, `SEARCH_REASONING_EFFORT=low`. Optional local controls: `SEARCH_LOCAL_MODEL`, `SEARCH_MODEL_CACHE_DIR` and the resource limits above. `SEARCH_OPENAI_BASE_URL` defaults to `https://api.openai.com/v1/` and accepts an operator-specified HTTP(S) base endpoint without embedded credentials. Invalid provider configuration degrades to fuzzy search and does not download a model. No key means hosted requests do not run, and lexical fallback reports unavailable configuration. Local and fuzzy modes must never call OpenAI even if a key is present.

Hosted search is a bounded reranker over scoped lexical/local candidates, not a workspace-writing agent. Send at most ~40 candidates/~24 KiB text, cancel/timeout at ~8 seconds, limit concurrent calls, limit query frequency, cache identical query/candidate hashes briefly and cap output tokens (e.g. 512). Use Responses with `store:false`, `reasoning:{effort}`, no tools, and strict `text.format` JSON schema containing only ranked candidate IDs. Put instructions in the developer message and user query/candidate JSON in a data message; explicitly treat every note as untrusted data. Validate IDs against the candidate set, uniqueness and maximum count; never use model-generated text as a snippet. Handle refusal/incomplete/malformed/rate-limit/timeout responses by retaining lexical results. Never automatically switch a local request to paid hosted search, and never log keys, full notes or upstream request bodies.

The implemented hosted adapter keeps the exact lexical tier even when the model omits it, includes representative field snippets with 70-byte per-field and 600-byte per-candidate caps, and checks actual list/category source hashes after inference. It admits one hosted request at a time, at least one second apart and at most ten per minute; cache hits are free. It accepts at most 64 KiB upstream response bytes before aborting. Hosted candidate coverage is deliberately bounded to 40 lists and short representative snippets, so it cannot promise full-note recall for large workspaces. Unit tests cover provider failure/omitted exact IDs, malformed foreign IDs, in-flight category rename with unchanged list timestamps, no-key behavior, throttling and idle disposal. No paid API request was made for this research or test pass.
